# 站长手册

## 网站怎么运作

GitHub Pages 提供网页、图片和音乐目录。登录与留言通过 HTTPS 请求 Railway 后端；SuperTokens 负责身份验证，留言保存在数据库里。因此，页面能打开不代表登录和留言也正常。

推送到 main 后，GitHub Actions 会运行检查并发布网站。Railway 的部署需要单独确认。每周播放量刷新任务会直接更新 main，不要随意禁止直接推送；如需改成必须审核，应先调整自动更新流程。

## 每次改完看什么

1. 本地运行 `npm test`、`npm run check`、`npm run test:integration`、`npm run check:changelog`，都成功再提交。最后一项单独联网核对上线记录；`npm run check` 本身不查询 GitHub API。测试失败时先找原因，不要删除安全检查来通过测试。
2. 在 GitHub Actions 查看对应提交的 `Verify website` 和 `Publish public site`，两项都应成功。
3. 打开网站确认页面正常，再检查后端 `/healthz`：`ok` 应为 `true`，`version` 应与部署提交前七位一致。健康检查成功不等于所有登录、留言功能都验证过。
4. 记录提交号、两项工作流的运行编号和后端版本。没有核实就写“待确认”，不要写“已上线”。
5. 将访客可感知的变化补进 [更新日志](CHANGELOG.md)：一行一条，写「症状 → 处理（提交号）」。测试、内部重构和依赖升级留在提交记录中。
6. 部署验证完成后，同步本地文本副本：运行 `python3 inabakumori-site-all-code/sync.py`，再运行 `python3 inabakumori-site-all-code/sync.py --check`，确认副本与当前已提交源码逐字节一致。保留现有 `.review-base`，除非维护者要求重置。维护者已授权 AI 执行同步与校验；本地脚本及副本仍由 `.gitignore` 排除，不提交、不部署。

副本保留原始缩进和字节，按完整源文件拆卷，每段以 `===== 文件路径 =====` 开头，每卷最多 150,000 字节。优先控制在 10 个 txt 以内，必要时不超过 15 个；排除生成的 `js/auth.js`、两个 `package-lock.json`、`dist/`、二进制、环境变量、数据库及密钥。全站复核只提供 `1-app-code`、`2-tools-tests`、`3-docs` 三组分卷；只核对改动时只提供 `changes.txt`，同一提问不要同时提供重叠内容。

## 核对上线记录表

运行 `npm run check:changelog`，读取 GitHub Actions 的真实运行记录，核对现有表行的提交、工作流、日期、重复项与时间顺序。同一行有多个提交时按先后排列，最后一个对应主 Verify / Publish 运行；括号内的历史运行须注明对应提交。跨日的主运行对取较早创建的运行，以 `America/Los_Angeles` 换算日期。

本地可使用已配置的 `GITHUB_TOKEN` 或 `GH_TOKEN` 提高查询限额，不把令牌写入文件或提交。CI 为该步骤提供 `GITHUB_TOKEN` 和只读 Actions 权限。重试后仍失败、限流未解除、运行记录缺失、空表或零覆盖都必须非零退出；只有实际核对全部所列运行后才能报告通过。

命令行以每页 100 条分页读取运行列表，只有未找到的运行号才逐个补查，所列运行数不等于请求数。默认在已忽略的 `artifacts/changelog-api-cache.json` 保存公开响应、ETag 和匿名限流冷却信息，不保存令牌或 Authorization 请求头。每次成功核对都须联网取得 `200`，或由服务器返回 `304` 确认对应缓存仍有效；不能在断网或 API 失败时拿旧缓存改报通过。`npm run check:changelog -- --no-cache` 完全跳过本地缓存读写，仍须联网核对。

GitHub 仅保证携带有效 Authorization 的条件请求在收到 `304` 时不占用主请求额度；匿名请求即使使用 ETag，也不能保证省额度。详见 [GitHub 条件请求说明](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests)。

默认模式发现匿名请求的 `x-ratelimit-remaining` 为 `0` 时，保存冷却至 `x-ratelimit-reset`；之后在恢复时间前快速失败并提示恢复时间与令牌配置方式，不继续消耗请求。配置令牌后不沿用匿名冷却，但仍受该令牌自己的配额限制。短暂网络故障、5xx 或短 `Retry-After` 仅作有界重试；较长限流直接失败，不能在服务器要求的等待时间内密集重试。无明确恢复时间的二级限流也不能立即重试；GitHub 要求至少等待一分钟，详见 [GitHub 限流处理说明](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#exceeding-the-rate-limit)。

此前遇到的 `403` 仍是当时真实的校验失败，后续重试成功不改写该历史结果。GitHub API 的故障仍可能使本地门禁和 `Verify website` 失败；恢复后应重跑，不能跳过记录。`Publish public site` 独立运行，不会自动等待这项检查；发布后仍须确认两条工作流都成功。

当前表格仅接受 `main` 分支上由 `push` 触发的 Verify / Publish 运行。若以后要记录 `workflow_dispatch` 手动部署，应先扩展事件校验规则和测试，再填写对应运行号。

此检查验证已记录的行，不自动追加新行，也不检查是否漏记推送。通过时只报告「已记录的行与运行核对通过」，不能据此报告「记录已最新」。另行核对覆盖范围时，先固定截止提交，再将此前实际推送与表格逐项比对，并报告截止提交；本次写表提交自身遵循「晚一行」约定，留待下次补记。

## 出问题先看哪里

| 现象 | 先检查 |
| --- | --- |
| 页面不更新或发布失败 | GitHub Actions 的发布记录，确认看的是本次提交 |
| 页面正常，登录或留言失败 | Railway 部署状态和错误日志，再看 SuperTokens 服务状态 |
| 域名打不开或证书报错 | 域名服务商与 GitHub Pages 的域名、HTTPS 状态 |
| 数据异常或误删 | 保留现有数据，确认备份可读，先在隔离环境演练恢复 |
| 怀疑凭证泄露 | 在对应平台撤销或轮换凭证，撤销相关会话，检查账号活动记录 |

求助时只分享脱敏后的错误信息。不要把完整日志、备份或内部审计报告直接贴到公开 issue。紧急回退应使用已知正常的提交并重新验证；数据库恢复另行处理，不能靠代码回退恢复数据。

## 哪些不能随手改

- 不公开密码、令牌、验证码、恢复码或数据库备份；不把这些内容放进前端代码。
- 不关闭 HTTPS、身份验证、权限检查或请求大小限制来“临时修好”功能。
- 不仅凭邮箱给人管理员权限；账号、域名和风险接受的决定由所有者确认。
- 不添加账号级登录失败锁定，避免他人反复失败把账号所有者锁在门外。
- 不随意扩容后端副本或更换代理入口；先评估数据库、限流和真实访客 IP 的处理。

## 换了图片、图标怎么办

把 `images/` 里的图片换成新文件后，**一定要把引用它的网址末尾版本号 +1**（例如 `images/X.png?v=3` 改成 `?v=4`），否则访客会继续看到旧图：浏览器、微信/小红书这类内置浏览器、手机主屏图标都是按"完整网址"缓存的，文件换了但网址没变，它们就不会重新下载。

- 社交图标：改 `index.html` 里的 `?v=`。
- 手机首屏大图：同时更新 `index.html` 的预加载和 `<source>`、`js/config.js` 中第一张手机图的 `?v=`，三个地址必须一致，避免初始化或轮播后又显示缓存旧图。
- 网页图标（favicon / 主屏图标）：改 `index.html` 和 `site.webmanifest`，**整组一起 +1**（`?v=3` → `?v=4`），主屏图标最"粘"，整组更新最省心。
- 只改文字、样式、脚本则不用管：构建时会自动给它们算出新的 `?v=` 指纹。

## 构建产物里的隐藏文件

用 Finder 打开过 `dist/`、`images/` 等目录后，macOS 会生成 `.DS_Store`。这类文件不会被发布（GitHub Pages 对点文件返回 404），构建也会自动把它们从产物里清掉，`check-build` 还会在发现其它点文件时直接让构建失败。

- 不需要手动删除，构建时会清理；`.nojekyll` 是唯一有意发布的点文件。
- 不要用 `git add -A` 把 `.DS_Store` 提交进仓库（`.gitignore` 已忽略，但仍要留意）。

## 平时要做的事

查看安全告警和依赖更新，备份后定期在隔离环境验证恢复。轮换管理员密码时，确认仍为 ≥20 位随机且全站唯一。平台账号启用两步验证，并妥善保存恢复方式；完成这一轮加固后，这些维护仍需继续。

以下项目截至本次文档编写均**待维护者确认**，不代表已启用或未启用：GitHub、Railway、SuperTokens、域名服务商的两步验证；GitHub 的 Secret scanning、Push protection、Dependabot alerts。由维护者逐项核实，在私有运维记录中写明状态、确认人和确认日期，不在公开文档记录个人身份或恢复信息。

## 真机抽检清单（每次发布后约 2 分钟）

模拟设备（WebKit + 触摸手势 + iPhone 视口）已经跑过同样步骤，真机仍建议抽检一次：差异主要在触摸手势的手感与键盘弹起行为。在手机上打开 <https://osagechan.top/>，依次做 4 件事：

1. **画廊拖拽跟手**：手指按住插画行左右拖动，轨道应跟随手指；松手后不要出现页面跳动。
2. **拖出来的插画不是空白框**：继续拖到第 16 张之后，新进入视野的缩略图应在 1 秒内出现画面；若只见空白方块，记下机型与系统版本。
3. **轻点打开大图**：轻点任意插画应打开灯箱，图注显示「NKNK 插画 N · i / 107」（共 107 张）；用 ‹ › 切换时画面不重叠、计数正确。
4. **关闭后回到原处**：点 × 关闭，页面应回到打开前的位置，画廊继续自动滚动（不再暂停）。

有键盘时（iPad 或外接键盘）再确认两点：打开灯箱时按 `/` 不应跳到背后的搜索框；在画廊里按方向键 / End 跳转时缩略图同样不应出现空白框。

发现问题请记录：机型 / 系统版本 / 浏览器（Safari 或微信内置）/ 复现步骤 + 一张截图，即可定位。
