# 站长手册

## 网站怎么运作

GitHub Pages 提供网页、图片和音乐目录。登录与留言通过 HTTPS 请求 Railway 后端；SuperTokens 负责身份验证，留言保存在数据库里。因此，页面能打开不代表登录和留言也正常。

推送到 main 后，GitHub Actions 会运行检查并发布网站。Railway 的部署需要单独确认。每周播放量刷新任务会直接更新 main，不要随意禁止直接推送；如需改成必须审核，应先调整自动更新流程。

## 每次改完看什么

1. 本地运行 `npm test`、`npm run check`、`npm run test:integration`、`npm run check:changelog`，都成功再提交。最后一项单独联网核对上线记录；`npm run check` 本身不查询 GitHub API。测试失败时先找原因，不要删除安全检查来通过测试。
2. 在 GitHub Actions 查看对应提交的 `Verify website` 和 `Publish public site`，两项都应成功。
3. 打开网站确认页面正常，再检查后端 `/healthz`：`ok` 应为 `true`，`version` 应与部署提交前七位一致。健康检查成功不等于所有登录、留言功能都验证过。
4. 记录提交号、两项工作流的运行编号和后端版本。没有核实就写“待确认”，不要写“已上线”。
5. 将访客可感知的变化补进 [更新日志](CHANGELOG.md)：一行一条，写「症状 → 处理（提交号）」。测试、内部重构和依赖升级留在提交记录中。
6. 部署验证完成后，同步本地文本副本：运行 `python3 tools/sync-copy.py`，再运行 `python3 tools/sync-copy.py --check`，确认副本与当前已提交源码逐字节一致。保留现有 `.review-base`，除非维护者要求重置。生成器及其回归测试受版本控制；生成的副本仍由 `.gitignore` 排除，不提交、不部署。旧的 `inabakumori-site-all-code/sync.py` 仅为本地兼容入口，规则只维护在 `tools/sync-copy.py`。

副本保留原始缩进和字节，按完整源文件拆卷，每段以 `===== 文件路径 =====` 开头，每个 txt 最多 130,000 字节，数量随完整源文件体积自动调整，不设固定份数。单个源文件连同段头超限时明确失败；`changes.txt` 仍保留为一个文件，超限时须由维护者明确调整复核基线，不自动拆分或重置。排除生成的 `js/auth.js`、两个 `package-lock.json`、`dist/`、二进制、环境变量、数据库及密钥。全站复核只提供 `1-app-code`、`2-tools-tests`、`3-docs` 三组分卷；只核对改动时只提供 `changes.txt`，同一提问不要同时提供重叠内容。

## 核对上线记录表

运行 `npm run check:changelog`，读取 GitHub Actions 的真实运行记录，核对现有表行的提交、工作流、日期、重复项与时间顺序。同一行有多个提交时按先后排列，最后一个对应主 Verify / Publish 运行；括号内的历史运行须注明对应提交。跨日的主运行对取较早创建的运行，以 `America/Los_Angeles` 换算日期。

`npm run check:changelog:structure` 只读取本地的真实更新日志，检查表头、行格式、提交和运行号格式、重复项，以及表格非空；坏表非零退出。它不读取 Git 历史、覆盖配置或 API 缓存，不联网核实运行号归属、日期或推送覆盖。该命令已接入 `npm run check`，因此 PR、功能分支和手动运行都会实际执行表格结构校验。报告时应区分「本地结构通过」与「GitHub 记录在线核对通过」。

正常本地维护的前置准备是通过当前终端或凭证管理器配置只读 `GITHUB_TOKEN` 或 `GH_TOKEN`，不要把令牌写入项目文件、提交或聊天。脚本不会从系统钥匙串提取凭证。无令牌时仍可作匿名诊断，但共享的 60 次/小时配额可能耗尽并阻止提交，这种 `403` 不代表代码错误。CI 为该步骤提供 `GITHUB_TOKEN` 和只读 Actions 权限。重试后仍失败、限流未解除、运行记录缺失、空表或零运行核对都必须非零退出；只有实际核对全部所列运行后才能报告通过。

命令行以每页 100 条分页读取运行列表，只有未找到的运行号才逐个补查，所列运行数不等于请求数。默认在已忽略的 `artifacts/changelog-api-cache.json` 保存公开响应、ETag 和匿名限流冷却信息，不保存令牌或 Authorization 请求头。每次成功核对都须联网取得 `200`，或由服务器返回 `304` 确认对应缓存仍有效；不能在断网或 API 失败时拿旧缓存改报通过。`npm run check:changelog -- --no-cache` 完全跳过本地缓存读写，仍须联网核对。

GitHub 仅保证携带有效 Authorization 的条件请求在收到 `304` 时不占用主请求额度；匿名请求即使使用 ETag，也不能保证省额度。详见 [GitHub 条件请求说明](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests)。

默认模式发现匿名请求的 `x-ratelimit-remaining` 为 `0` 时，保存冷却至 `x-ratelimit-reset`；之后在恢复时间前快速失败并提示恢复时间与令牌配置方式，不继续消耗请求。配置令牌后不沿用匿名冷却，但仍受该令牌自己的配额限制。短暂网络故障、5xx 或短 `Retry-After` 仅作有界重试；较长限流直接失败，不能在服务器要求的等待时间内密集重试。无明确恢复时间的二级限流也不能立即重试；GitHub 要求至少等待一分钟，详见 [GitHub 限流处理说明](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#exceeding-the-rate-limit)。

此前遇到的 `403` 仍是当时真实的校验失败，后续重试成功不改写该历史结果。GitHub API 的故障仍可能使本地门禁和 `Verify website` 失败；恢复后应重跑，不能跳过记录。`Publish public site` 独立运行，不会自动等待这项检查；发布后仍须确认两条工作流都成功。

当前表格仅接受 `main` 分支上由 `push` 触发的 Verify / Publish 运行。若某次 main 推送时 `Publish public site` 已停用、确实没有产生 Publish 运行，该行主运行对写作 `Verify 运行号 / —`；Verify 照常联网核对，覆盖核对若在运行列表中发现该提交有 Publish push 运行则失败，`—` 不能用于括号内的历史运行或掩盖失败的发布。若以后要记录 `workflow_dispatch` 手动部署，应先扩展事件校验规则和测试，再填写对应运行号。

CI 的联网记录校验只在 `push` 到 `refs/heads/main` 时执行。PR、其他分支或标签的推送、手动运行均跳过这一步，继续执行包含本地表格结构校验的 `npm run check`、认证构建产物一致性检查和集成测试。PR 默认检出合成的 merge commit，其 HEAD 与 main 的最后推送头不同，不能套用发布记录的当前 HEAD 例外，详见 [GitHub 的 PR 事件说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)。报告这些运行时应写「联网步骤跳过」，不能写「线上记录校验通过」；本地发布前仍须执行并通过四项门禁。

覆盖门禁使用受版本控制的 `tools/changelog-coverage.json` 中的完整提交 `since` 作基线，固定到当前检出的完整 `HEAD`，并用完整 Git 历史限定祖先范围。基线之后、这个范围内 GitHub 列表实际出现的 `main/push` Verify / Publish 提交必须出现在表行的最后一个提交位置；基线本身也必须保留主表行，除非它就是当前 HEAD。不能把仅随同推送的中间提交误当成单独推送。CI 因此必须检出完整历史，`GITHUB_SHA` 如存在也必须与检出提交相同。

唯一可暂缺的范围内推送是当前检出的 `HEAD`：本次写表提交的运行号在提交后才产生，按「晚一行」约定留待下一次补记。不能任意豁免最新两行，也不自动填表。配置同时固定基线的原始 Verify / Publish 运行号；运行列表必须读到这两个具体锚点，并完成表内所有运行核对，不能在后来同 SHA 的再次推送处提前停止。分页上限、缺失锚点或列表不完整均失败。输出会分别给出已有行一致性、覆盖起止提交、观测到的推送数、已有行数及当前提交的例外。

本轮启用的基线为 `5e6c2d41b1048ca803a3c5d5605eede7d5b1ce04`。基线以前的表行仍核对一致性，不声称已查尽更早的遗漏；从未产生目标工作流或记录已删除的推送也不能由运行列表凭空还原。基线等于当前提交时会明确报告尚无新增推送范围，不能称为全历史覆盖。报告须注明实际起止提交，不能将通过描述成「记录已最新」。

覆盖分页上限为 10 页、每页 100 个运行；GitHub 对带分支或事件筛选的单次查询也最多返回 1,000 个结果，详见 [运行列表 API](https://docs.github.com/en/rest/actions/workflow-runs?apiVersion=2022-11-28#list-workflow-runs-for-a-repository)。随着记录增长，应在旧锚点仍可读取时先完成旧范围核对，再选取已有主表行、两条目标工作流均已核实的 main 祖先提交，同时更新配置中的完整 `since` 和 Verify / Publish 顺序的 `baselineRunIds`，记录旧、新起止提交及核对依据，重新运行四项门禁。

若已触及分页上限或旧锚点无法读取，应先用带 `created` 时间窗的查询（各窗少于 1,000 条、交界重叠并去重）或可信的历史核验记录补足旧范围证据。证据不足继续报告失败；不得自动前移基线、只调大页数或用新范围通过掩盖旧范围失败。覆盖配置与副本 `.review-base` 分别维护；后者只决定 `changes.txt` 的差异范围，仍须维护者明确授权才能修改。

同一轮由负责最终提交的执行者独占补表；其他协作者只提供核对结果。写入前重新读取 HEAD 与表格，核实主运行对的完整提交、运行号和日期，再补上此前缺行。重复检测是最后防线，不代替这项分工。

规则只在本节维护；协作约定、表头和历史记录引用本节，避免各自保留不同版本。

## 出问题先看哪里

| 现象 | 先检查 |
| --- | --- |
| 页面不更新或发布失败 | GitHub Actions 的发布记录，确认看的是本次提交 |
| 页面正常，登录或留言失败 | Railway 部署状态和错误日志，再看 SuperTokens 服务状态 |
| 域名打不开或证书报错 | 域名服务商与 GitHub Pages 的域名、HTTPS 状态 |
| 数据异常或误删 | 保留现有数据，确认备份可读，先在隔离环境演练恢复 |
| 怀疑凭证泄露 | 在对应平台撤销或轮换凭证，撤销相关会话，检查账号活动记录 |

求助时只分享脱敏后的错误信息。不要把完整日志、备份或内部审计报告直接贴到公开 issue。紧急回退应使用已知正常的提交并重新验证；数据库恢复另行处理，不能靠代码回退恢复数据。

## 哪些不能随手改

- 不公开密码、令牌、验证码、恢复码或数据库备份；不把这些内容放进前端代码。
- 不关闭 HTTPS、身份验证、权限检查或请求大小限制来“临时修好”功能。
- 不仅凭邮箱给人管理员权限；账号、域名和风险接受的决定由所有者确认。
- 不添加账号级登录失败锁定，避免他人反复失败把账号所有者锁在门外。
- 不随意扩容后端副本或更换代理入口；先评估数据库、限流和真实访客 IP 的处理。

## 换了图片、图标怎么办

把 `images/` 里的图片换成新文件后，**一定要把引用它的网址末尾版本号 +1**（例如 `images/X.png?v=3` 改成 `?v=4`），否则访客会继续看到旧图：浏览器、微信/小红书这类内置浏览器、手机主屏图标都是按"完整网址"缓存的，文件换了但网址没变，它们就不会重新下载。

- 社交图标：改 `index.html` 里的 `?v=`。
- 手机首屏大图：同时更新 `index.html` 的预加载和 `<source>`、`js/config.js` 中第一张手机图的 `?v=`，三个地址必须一致，避免初始化或轮播后又显示缓存旧图。
- 网页图标（favicon / 主屏图标）：改 `index.html` 和 `site.webmanifest`，**整组一起 +1**（`?v=3` → `?v=4`），主屏图标最"粘"，整组更新最省心。
- 只改文字、样式、脚本则不用管：构建时会自动给它们算出新的 `?v=` 指纹。

## 构建产物里的隐藏文件

用 Finder 打开过 `dist/`、`images/` 等目录后，macOS 会生成 `.DS_Store`。这类文件不会被发布（GitHub Pages 对点文件返回 404），构建也会自动把它们从产物里清掉，`check-build` 还会在发现其它点文件时直接让构建失败。

- 不需要手动删除，构建时会清理；`.nojekyll` 是唯一有意发布的点文件。
- 不要用 `git add -A` 把 `.DS_Store` 提交进仓库（`.gitignore` 已忽略，但仍要留意）。

## 平时要做的事

### 最新动态页面

首页「最新动态」导航滚动到同页的 `#updates` 栏目，直接阅读、按创作者筛选并分批展开。`updates.html` 保留为兼容入口。两处均使用 `data/creator-updates.json` 的同一份公开元数据，构建时生成静态列表，访客无需跨域请求官方平台；标题保留原文，说明、筛选、语言和主题支持中英日。作品发布时间与来源的成功核对时间分别显示，日本时间标为 JST。

`Refresh creator updates` 每天一次（UTC 11:17，即太平洋时间 04:17 PDT / 03:17 PST）计划运行，也可在 Actions 手动运行，GitHub 的定时任务可能延迟。当前自动范围是稲葉曇官方 YouTube 频道的新视频、NKNK 官方 pixiv 的公开插画、CAMPFIRE 项目 `970332` 主办方的活动报告；合作公告不是作者本人发帖，该轮众筹已于 2026-09-23 结束。X 只提供本人入口，不能把此页面称作实时或完整的社交动态。pixiv 最近公开投稿较旧，仍按实际发布时间展示。

本地更新运行 `node tools/refresh-creator-updates.mjs`。不需要平台密钥；YouTube RSS 不可用时退回本人公开视频页面，并逐条验证频道与绝对发布时间。源失败时保留此前条目和 `checkedAt`，只更新尝试时间与失败状态，命令非零退出；超过 72 小时未成功检查时，页面也会提示可能过期。成功检查若与上次快照相比条目、来源状态和提示均无变化，脚本不改写快照，工作流因此不提交、不发布；仅当已记录的成功检查时间超过 36 小时时写入一次心跳，使页面显示的核对时间保持在 72 小时内。失败来源只更新尝试时间时同样不提交。平台结构变化需修复解析器，不得编造时间或将失败当作成功。

定时流程先用 `tools/record-current-deployment.mjs` 补记当前 HEAD 已真实完成的 main/push 主运行对，再执行四项门禁。该辅助只用于本流程，遵守上文同一轮由最终提交执行者独占补表的约定；不改覆盖基线，不把手动派发运行填进主表。上次 bot 提交若仅产生 dispatch 运行，核实后无需另记 main/push 表行，原覆盖门禁仍照常运行。读取与检查作业只读，后续单独作业仅提交已检查的快照与日志；HEAD 变化时拒绝推送，等待下次检查，避免覆盖并发修改。

`GITHUB_TOKEN` 推送不自动触发 push 工作流，因此更新后显式派发 Verify 和 Publish，按快照提交等待两者成功，并核对线上 `creator-updates-version` 指纹。来源读取失败的状态也会发布，但刷新工作流最终仍报告失败。若发布或核验失败，应查看对应提交的工作流，不能把派发成功描述成已发布。本机源码副本仍在人工维护完成线上核验、拉取最新提交后，按前文约定同步；线上定时作业不访问本机副本。

### X 帖子原文档案

首页「最新动态」先展示两位创作者各最近 6 条 X 公开帖子原文（`js/x-posts-home.js` 只切换已预渲染条目的 `hidden`，按创作者筛选），`updates.html` 及 `updates-<creator>[-page-N].html` 每页 30 条分页展示全部已收录帖子，构建时追加进 `dist/sitemap.xml`。数据在 `data/x-posts/`（`manifest.json` 加按内容哈希命名、单个不超过 120,000 字节的分片），只收原创帖与引用帖，不含回复、转发和自回复串；正文保持原文，图片和视频只提示「请到原帖查看」，不嵌入 X 内容，CSP 不变。

导入：把扫描结果写成 `tools/x-posts-data.mjs` 定义的格式（`{version: 1, coverage, items}`，完整正文、`translated: false`），放在不提交的位置（如 `artifacts/`），运行 `node tools/import-x-posts.mjs <scan.json>`。同一 ID 的正文、作者或时间不一致会保留旧值并列为冲突、命令非零退出，需人工核对。原始扫描文件不提交。覆盖范围始终标为 partial，并记录扫描区间与中断原因。档案页单独计入 20 MiB 预算，其余公开文件仍受 12 MiB 限制。


`npm run check` 包含最小 ESLint 门禁：检查未定义名称和变量/类的提前引用；允许普通函数声明提前调用。它覆盖前端、后端、工具与测试，排除生成的认证包和本地副本。

`Audit dependencies` 每周一 16:00 UTC 分别审计网站（含开发依赖）和后端的锁文件，也支持手动运行。审计失败应检查实际漏洞或网络错误；它不随每次推送运行，不阻塞两条发布工作流。本地可运行 `npm audit --package-lock-only` 和 `npm --prefix backend audit --package-lock-only` 复核。

查看安全告警和依赖更新，备份后定期在隔离环境验证恢复。轮换管理员密码时，确认仍为 ≥20 位随机且全站唯一。平台账号启用两步验证，并妥善保存恢复方式；完成这一轮加固后，这些维护仍需继续。

## 真机抽检清单（每次发布后约 2 分钟）

模拟设备（WebKit + 触摸手势 + iPhone 视口）已经跑过同样步骤，真机仍建议抽检一次：差异主要在触摸手势的手感与键盘弹起行为。在手机上打开 <https://osagechan.top/>，依次做 4 件事：

1. **画廊拖拽跟手**：手指按住插画行左右拖动，轨道应跟随手指；松手后不要出现页面跳动。
2. **拖出来的插画不是空白框**：继续拖到第 16 张之后，新进入视野的缩略图应在 1 秒内出现画面；若只见空白方块，记下机型与系统版本。
3. **轻点打开大图**：轻点任意插画应打开灯箱，图注显示「NKNK 插画 N · i / 107」（共 107 张）；用 ‹ › 切换时画面不重叠、计数正确。
4. **关闭后回到原处**：点 × 关闭，页面应回到打开前的位置，画廊继续自动滚动（不再暂停）。

有键盘时（iPad 或外接键盘）再确认两点：打开灯箱时按 `/` 不应跳到背后的搜索框；在画廊里按方向键 / End 跳转时缩略图同样不应出现空白框。

发现问题请记录：机型 / 系统版本 / 浏览器（Safari 或微信内置）/ 复现步骤 + 一张截图，即可定位。

## 已知测试缺口

- **`loadMoreFocus` 的"请求期间有行被删"分支已不再是缺口**（2026-10-16 更新）：DOM 替身补齐了 `lastElementChild` 与 `nextElementSibling`，该用例对旧逻辑失败、对当前逻辑通过，可同时作为红证据与绿证据。
- `loadMoreFocus` 保留现有元素身份判断：请求期间删后复用同一行不算新留言；整表重建时首行算新留言。这两项作为当前产品行为，不为接入维护门禁改动。
